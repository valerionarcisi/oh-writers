Architettura AI agentic di Cesare

Come funziona l'AI di Oh Writers, capitolo per capitolo · pattern, numeri, trade-off, decisioni · main · 2026-05-27

Questo documento racconta come è costruita la parte AI di Oh Writers — l'assistente in-prodotto si chiama Cesare in omaggio a Cesare Zavattini. È pensato per chi sa programmare ma non ha background ML: ogni capitolo spiega il perché prima di mostrare il come. I numeri citati vengono da vernissage/cost-foundation.md e dal codice in apps/web/app/features/predictions/.

1. Perché parliamo di AI agents oggi

Un chatbot statico riceve un messaggio, chiama l'LLM una volta, ritorna la risposta. Un agente invece può fare cose: chiamare funzioni server, leggere dati, proporre mutazioni, e ricominciare il ragionamento usando i risultati di quelle azioni. Il loop dura finché il modello smette di chiedere strumenti — o finché tagliamo noi.

Cesare non è un chatbot. È un agente che vede il contesto della produzione (scene, budget, schedule, locations, breakdown), chiama tool tipizzati per leggere o proporre modifiche, e ragiona iterativamente sui risultati. La differenza pratica è che l'utente scrive "che dice John nella scena 1?" e Cesare non risponde a memoria: chiama read_scene(1), riceve il testo, poi cita la battuta letterale.

2. Il pattern centrale: tool-use loop

Tutto il comportamento agentic di Cesare gira attorno a una funzione di una sessantina di righe: runGenericToolLoop in cesare-tools.ts. È la spina dorsale di ogni page context — soggetto, sceneggiatura, breakdown, budget, schedule, shooting-plan, locations. Le specializzazioni cambiano solo l'executor e il set di tool disponibili, non il loop.

Pseudo-codice del ciclo

const MAX_ITERATIONS = 5;
let messages = [...userTurn];

for (let i = 0; i < MAX_ITERATIONS; i++) {

  // 1. Chiama il modello con system prompt + storia + tool definitions
  const response = await client.messages.create({
    model,            // haiku-4-5 o sonnet-4-6, scelto dal router
    system,           // SystemPromptBlock[] con cache_control ephemeral
    messages,
    tools,            // schema JSON dei tool della pagina
    max_tokens: 1500,
  });

  // 2. Stop condition: niente tool_use → il modello ha finito
  if (response.stop_reason !== "tool_use") break;

  // 3. Esegui i tool che il modello ha richiesto in questo turno
  const results = [];
  for (const block of response.content.filter(isToolUseBlock)) {
    const result = await executor(block, db, projectId);
    results.push({ type: "tool_result", tool_use_id: block.id, content: ... });
  }

  // 4. Appendi assistant turn + user turn coi tool_result, ricomincia
  messages.push({ role: "assistant", content: response.content });
  messages.push({ role: "user",      content: results });
}

Lo stesso loop, dal codice reale

File: apps/web/app/features/predictions/cesare-tools.ts · è la funzione che ogni page context (soggetto, sceneggiatura, breakdown, budget, schedule, shooting-plan, locations) chiama come spina dorsale dell'agente: ogni feature passa il proprio executor e il proprio set di tools, il loop resta lo stesso. 

const runGenericToolLoop = (
  args: RunToolLoopArgs,
): ResultAsync<string, CesareError> =>
  ResultAsync.fromPromise(
    (async (): Promise<string> => {
      const MAX_ITERATIONS = 5;
      const currentMessages: Message[] = [...args.messages];
      const textAccumulator: string[] = [];

      for (let i = 0; i < MAX_ITERATIONS; i++) {
        const response = await args.client.messages.create({
          model: args.model,
          max_tokens: 1500,
          system: args.systemPrompt,
          messages: currentMessages,
          tools: args.tools,
          tool_choice: { type: "auto" },
        });

        const toolBlocks = response.content.filter(isToolUseBlock);
        // ... raccolta dei text block nel textAccumulator

        if (response.stop_reason !== "tool_use" || toolBlocks.length === 0) {
          break;
        }

        const toolResults: ToolResult[] = [];
        for (const block of toolBlocks) {
          const result = await args.executor(block, args.db, args.projectId);
          if (result.isErr()) {
            toolResults.push({
              type: "tool_result",
              tool_use_id: block.id,
              content: JSON.stringify({ error: result.error.message }),
            });
          } else {
            toolResults.push(result.value);
            // side-channel marker per propose_blocking_for_scene...
          }
        }

        currentMessages.push({ role: "assistant", content: response.content });
        currentMessages.push({ role: "user", content: toolResults });
      }
      // ... (vedi file completo per il marker finale e il return)
    })(),
    (e) => new CesareError(`tool loop failed: ${...}`),
  );

Cosa imparare da questo codice

  • Il loop è puro controllo: niente logica di dominio, niente conoscenza dei tool — solo "chiama modello → se chiede tool, esegui, ricomincia".
  • stop_reason !== "tool_use" è l'unica condizione di uscita "normale"; il cap a MAX_ITERATIONS = 5 è la rete di sicurezza per i casi patologici.
  • Gli errori dell'executor non escono dal loop: vengono serializzati come tool_result con campo error — il modello li legge e può ri-provare o spiegare all'utente.

Perché il cap a 5

Un agente che cicla all'infinito è un agente che brucia soldi. Il cap a 5 iterazioni è una scelta deliberata di fail-safe: se Cesare a iterazione 5 non ha ancora prodotto una risposta testuale, accetta che il turno finisca lì e l'utente potrà chiedere di nuovo. In pratica le conversazioni reali finiscono in 1–3 iterazioni. Il limite protegge dai casi patologici, non da quelli normali.

Detail tecnico — Cesare usa un side-channel invisibile per superare la barriera "il modello restituisce testo, ma il front-end deve disegnare overlay". Quando il tool propose_blocking_for_scene ha successo, il loop inserisce nel testo finale un commento HTML <!--ohw:blocking-proposal:…-->. Il front-end CesareSheet lo parsa, lo nasconde dal rendering, e dispatcha un DOM event che il canvas dello shooting-plan ascolta. Niente WebSocket dedicati, niente stream parser custom: solo testo arricchito.

3. RAG lazy — la nostra differenza dal RAG classico

Questo è il capitolo più importante. Se torni qui tra sei mesi cercando di spiegare a un investor "in cosa l'AI di Oh Writers è diversa", parti da qui.

Cos'è il RAG classico

RAG = Retrieval Augmented Generation. Lo schema canonico è: hai una pila di documenti non strutturati (PDF, pagine wiki, manuali, articoli). Li spezzi in chunks, li passi a un modello di embedding, salvi i vettori in un vector store (Pinecone, Weaviate, pgvector). Quando arriva una query dell'utente, generi l'embedding della query, cerchi per similarità coseno i top-k chunks più rilevanti, li infili nel prompt prima della domanda. Il modello risponde "ancorato" a quei chunks.

Funziona ottimamente quando: (a) i dati sono testo libero, (b) sono troppi per stare nel context window, (c) l'utente li interroga senza sapere cosa cerca precisamente. Pensa a un chatbot di assistenza che ha 10.000 articoli di knowledge base: l'embedding search è il modo giusto per recuperare i 3-4 rilevanti.

Perché NON usiamo il RAG classico

I dati di Oh Writers sono l'opposto di una knowledge base:

  • Sono strutturati — viviamo dentro PostgreSQL. Una scena ha number, heading, body, characterNames. Una riga budget ha topSheet, rate, quantity. Non c'è similarità da calcolare: c'è una chiave primaria.
  • L'utente lavora su questi dati, non li cerca — un produttore che scrive il budget sa che vuole modificare la riga "Crew giornata 1". Non sta facendo fuzzy-search "trova le voci che parlano di troupe".
  • Non c'è documento esterno da rintracciare — tutto il contesto vive nel DB del progetto. Aggiungere un vector store significherebbe duplicare lo stesso dato in due posti, e mantenerli sincronizzati.

Quindi: il vector store non risolve un problema che abbiamo. Aggiungerebbe latenza (un round-trip in più verso un servizio esterno), costo di hosting, complessità di sync. Per ottenere cosa? Una similarity search che già sappiamo risolvere con una WHERE di Drizzle.

Il pattern lazy che usiamo

Il sistema prompt di Cesare contiene solo l'essenziale sempre necessario: titolo progetto, indice delle scene (numero + heading, max 200 righe), lista personaggi, lista documenti del progetto. È un indice, non un contenuto. I dettagli li carica Cesare stesso, su richiesta, chiamando i tool read-only.

Cosa imparare da questo codice

  • I tool sono contratti, non funzioni: il modello li conosce solo da name, description e input_schema — il codice del corpo è completamente opaco a Claude.
  • as const congela i tipi così TypeScript può inferire gli input statici degli executors senza duplicare gli schemi.
  • Una description ben scritta vale più di un parametro in più: è il "prompt" privato che insegna al modello quando scegliere quel tool.

Un executor reale — read_scene

Stesso file, sezione Executors. Ogni read-tool è una query Drizzle puntuale che ritorna ResultAsync. Niente cache, niente embedding, niente vector store: solo una WHERE sul screenplayId + scene.number. 

const readSceneByNumber = (
  db: Db,
  projectId: string,
  sceneNumber: number,
): ResultAsync<unknown, CesareError> =>
  ResultAsync.fromPromise(
    (async () => {
      const [screenplay] = await db
        .select({ id: screenplays.id })
        .from(screenplays)
        .where(eq(screenplays.projectId, projectId))
        .limit(1);
      if (!screenplay) {
        return errPayload(`No screenplay for project ${projectId}`);
      }
      const [scene] = await db
        .select({
          id: scenes.id,         number: scenes.number,
          heading: scenes.heading, body: scenes.notes,
          intExt: scenes.intExt,  timeOfDay: scenes.timeOfDay,
          characterNames: scenes.characterNames,
        })
        .from(scenes)
        .where(
          and(
            eq(scenes.screenplayId, screenplay.id),
            eq(scenes.number, sceneNumber),
          ),
        )
        .limit(1);
      if (!scene) return errPayload(`Scene ${sceneNumber} not found`);
      return scene;
    })(),
    (e) => new CesareError(`read_scene failed: ${...}`),
  );

Cosa imparare da questo codice

  • Lo scope di tenancy è doppio: la WHERE usa sempre projectId come ancora — anche se withProjectAccess ha già autorizzato, qui si difende contro id confusion del LLM.
  • Il "non trovato" non è un'eccezione: ritorna un payload { error: "Scene N not found" } che il modello legge come tool_result e può ri-provare con un altro numero.
  • Una query puntuale < 1ms batte qualsiasi similarity search su dati strutturati. Non c'è "magia" da aggiungere.

Trade-off: numeri prima/dopo

Il costo di un'iterazione in più non è gratis: ogni read_* aggiunge un round-trip API. Ma il system prompt si dimezza, e dopo il primo passaggio il caching fa il resto. Numeri della baseline misurati sul progetto seed:

Metrica Prima (full payload) Dopo (lazy RAG) Δ
System prompt — input tokens medi ~ 18.000 ~ 9.200 −49 %
Domanda specifica (1 scena) — totale token ~ 20.500 ~ 11.000 + read_scene −40 %
Domanda generica ("che pensi?") ~ 18.000 ~ 9.200 + 0 tool −49 %
Latenza p50 (chat semplice) ~ 2.4 s ~ 1.9 s −21 %
Latenza p50 (chat con read) ~ 2.4 s ~ 3.1 s +29 %

La latenza aumenta del 29% sulle query che richiedono un read_scene, ma il costo crolla del 40-50% in token. Su scala (1000 query/giorno) il calcolo è semplice: −€7-10/giorno di costo Anthropic in cambio di +0.7s di latenza percepita.

La regola in una frase

Non passare al modello dati che il modello potrebbe non guardare. Dagli un indice e dei tool: lui decide cosa aprire.

4. Prompt caching (Anthropic ephemeral)

Anthropic permette di marcare blocchi del system prompt con cache_control: { type: "ephemeral" }. Quei blocchi vengono cachati a livello di infrastruttura Anthropic per ~5 minuti. Quando la stessa cache key si ripresenta (cioè lo stesso prefisso esatto di system prompt), Anthropic non ri-processa quei token: ti fattura il 10% del costo normale per la lettura dalla cache.

Quali blocchi cachiamo

buildSystemPrompt ritorna un array di 4 blocchi ordinati. I primi 3 sono cachati, il quarto no:

Blocco Contenuto Cache Perché
ROLE_TEXT "Sei Cesare, assistente AI di Oh Writers ispirato a Zavattini…" ephemeral Statico, non cambia mai dentro una sessione
CONTESTO PRODUZIONE Titolo, indice scene, lista personaggi, lista documenti ephemeral Cambia raramente — l'utente non aggiunge una scena ogni 3 secondi
TOOL GUIDANCE Istruzioni specifiche per la pagina (es. "su breakdown usa estimate_scene_cost…") ephemeral Funzione della pagina, stabile per tutta la permanenza in pagina
STATO DINAMICO Scena attiva, requirement attivo, day attivo, finestra scene heading no-cache Cambia ogni scroll / cambio focus — cachare = miss garantito

Il quarto blocco è la chiave: se lo cachi, ogni mossa dell'utente invalida la cache key e ti costa il full price per ri-costruirla. Lasciandolo fuori dal cache range, i primi tre blocchi restano caldi per 5 minuti continui.

Come si vede in codice

File: apps/web/app/features/predictions/cesare.server.ts · buildSystemPrompt ritorna l'array di blocchi che Cesare invia ad Anthropic come system. Tre blocchi marcati cache_control: ephemeral, l'ultimo no — questa è l'intera strategia di caching su un'unica funzione. 

const buildSystemPrompt = (
  ctx: CesareContext,
  page: PageContext["page"],
  activeShootingDayNumber: number | null = null,
  activeSceneId: string | null = null,
): SystemPromptBlock[] => [
  { type: "text", text: ROLE_TEXT, cache_control: { type: "ephemeral" } },
  {
    type: "text",
    text: buildProductionContextBlock(ctx),
    cache_control: { type: "ephemeral" },
  },
  {
    type: "text",
    text: buildToolGuidanceBlock(
      ctx,
      page,
      activeShootingDayNumber,
      activeSceneId,
    ),
    cache_control: { type: "ephemeral" },
  },
  {
    type: "text",
    text: buildDynamicStateBlock(ctx, page, activeShootingDayNumber),
  },
];

Cosa imparare da questo codice

  • L'ordine degli elementi nell'array è la cache key: Anthropic confronta il prefisso esatto, quindi spostare un blocco significa invalidare tutta la cache che lo precede.
  • Il blocco dinamico in coda (buildDynamicStateBlock) riceve scena/day attivi: cambia ad ogni interazione utente. Tenerlo fuori dal range cached protegge i tre blocchi caldi.
  • Tutto si decide al boundary di una pura funzione TypeScript: niente classi, niente builder, niente magia — solo un array letterale di shape.

Risparmio reale

Sulla seconda chiamata in poi nella stessa sessione (caso comune: l'utente fa 5-10 messaggi consecutivi), i blocchi ①②③ vengono fatturati al 10% del prezzo normale. Misurato sul seed, il prompt cachato pesa ~8500 token su 9200 totali del system prompt — quindi: 

chiamata 1: 9200 input tokens @ $3/M = $0.0276
chiamata 2: 700 input + 8500 cached @ 10% = $0.0021 + $0.00255 = $0.0046
saving %: (0.0276 - 0.0046) / 0.0276 = -83 %

Da qui il numero "−85% input dopo la 1ª chiamata" che vedi in sintesi.

5. Model tier router (Haiku vs Sonnet)

Non tutti i messaggi meritano un modello potente. "Che pensi?" non è una richiesta che richiede ragionamento complesso — chiamare Sonnet ($3/M input, $15/M output) è uno spreco. Haiku ($1/M input, $5/M output) la gestisce benissimo e in metà del tempo.

Il cesare-model-router.ts è una pure function: nessuna chiamata DB, nessun side-effect, nessuna chiamata API. Riceve userMessage, page, conversationLength, ritorna "haiku" o "sonnet". È testabile in <1ms con Vitest.

Le heuristics

  1. Stringa vuota → Sonnet (defensive default)
  2. Lunghezza > 200 char → Sonnet (i prompt lunghi codificano intent complesso)
  3. Conversazione > 4 turni → Sonnet (la storia accumula contesto da ragionarci)
  4. Verbo imperativo italiano → Sonnet (sta chiedendo una mutazione)
  5. Termina con "?" → Haiku (domanda pura, cheap)
  6. Default → Sonnet (preferiamo pagare di più che degradare qualità)

Il router per intero

File: apps/web/app/features/predictions/cesare-model-router.ts · è una pure function lato server eseguita prima della chiamata API. Niente DB, niente neverthrow (l'output non può fallire), niente React. Tutto qui sotto è letterale, copiato senza modifiche. 

export const HAIKU_MODEL  = "claude-haiku-4-5-20251001";
export const SONNET_MODEL = "claude-sonnet-4-6";

export type ModelTier = "haiku" | "sonnet";

export interface RouteModelInput {
  readonly userMessage: string;
  readonly page: CesarePage;
  readonly conversationLength: number;
}

// Italian imperative verbs that signal a state-changing request.
// False positives only cost us money (Sonnet when Haiku would have
// sufficed), false negatives cost correctness — Haiku tries to handle
// a mutation and fails. Stay permissive.
const ITALIAN_IMPERATIVE_REGEX =

const LONG_MESSAGE_CHAR_LIMIT      = 200;
const DEEP_CONVERSATION_TURN_LIMIT = 4;

export const routeModel = ({
  userMessage,
  page: _page,
  conversationLength,
}: RouteModelInput): ModelTier => {
  const trimmed = userMessage.trim();

  // Defensive: an empty message is not a real Haiku candidate.
  if (trimmed.length === 0) return "sonnet";

  // Long prompts encode complex intent. Don't gamble on Haiku.
  if (trimmed.length > LONG_MESSAGE_CHAR_LIMIT) return "sonnet";

  // Late-conversation messages carry accumulated context.
  if (conversationLength > DEEP_CONVERSATION_TURN_LIMIT) return "sonnet";

  // Imperative trumps everything (including "puoi aggiungere?").
  if (ITALIAN_IMPERATIVE_REGEX.test(trimmed)) return "sonnet";

  // Pure questions are cheap and Haiku handles them well.
  if (trimmed.endsWith("?")) return "haiku";

  // Default conservatively to Sonnet — we'd rather pay more than
  // degrade quality on an ambiguous prompt.
  return "sonnet";
};

Cosa imparare da questo codice

  • Decisione pura, deterministica, lato server, presa PRIMA della chiamata API. Latenza aggiuntiva: zero misurabile (regex su < 200 char).
  • L'ordine dei guard è la priorità: trigger imperative vincono su endsWith("?") (le mutazioni si formulano come domande gentili in italiano).
  • Default conservativo a Sonnet: in dubbio, paghiamo. Mai degradare la qualità per risparmiare cent.
Filosofia del falso positivo vs falso negativo — Un falso positivo (routing a Sonnet quando Haiku bastava) costa solo soldi. Un falso negativo (Haiku prova a gestire una mutazione complessa e sbaglia il tool call) costa correttezza. Quindi la regex è permissiva: in dubbio, ruoti verso Sonnet.

Esempi pratici

Messaggio Routing Motivo Costo stimato
"che pensi?" haiku Domanda corta, non imperativa, termina con ? ~ $0.001
"chi è il protagonista?" haiku Domanda informativa, no imperativo ~ $0.001
"scrivi la logline" sonnet Imperativo "scrivi" → mutazione ~ $0.015
"rinomina Marco in Luca in tutto il copione" sonnet Imperativo "rinomina" ~ $0.015
"il personaggio funziona ma vorrei che fosse più ambiguo, magari aggiungere una scena di dubbio prima del climax" sonnet > 200 char (intent complesso) + "aggiungere" ~ $0.020

Su distribuzione reale (cost-smoke), circa il 30-35% dei messaggi vanno su Haiku. Il risparmio medio è −70% sul costo di quel sottoinsieme, che si traduce in −20% sul costo complessivo Cesare.

6. Propose / Accept come pattern UX

Qui sta la differenza tra un agente utile e un agente pericoloso. Cesare non scrive mai direttamente nel DB cose che l'utente vede come "sue". Ogni mutazione passa attraverso una proposta esplicita, e l'utente deve accettarla.

Il principio sta in una frase: l'AI propone, l'umano dispone. È la nostra human-in-the-loop.

Perché agentic non deve mai auto-applicare

  • Errori catastrofici silenziosi — immagina "rinomina Mario in Lucia" che becca 200 occorrenze tra cui un dialogo "Mario è il fratello di Lucia" → 198 corrette, 2 nonsensicali. Senza accept-step, il danno è permanente fino a che l'utente se ne accorge (forse mai).
  • Fiducia dell'utente — il filmmaker deve sentire che lo strumento è suo, non che decide al posto suo. Un AI che "fa cose da solo" smette di essere assistente.
  • Reversibilità — la proposta vive in memoria, rifiutarla è gratis. Una mutazione DB richiede undo, log, versioning.

Due varianti: micro-edit e macro-edit

Micro-edit — decoration inline

Per modifiche puntuali, <400 char. Es: propose_screenplay_edit({ find, replace, reason }).

  • Il tool ritorna { from, to, replacement }
  • Un plugin ProseMirror disegna un overlay verde tratteggiato sopra il testo originale
  • I bottoni ✓ / ✕ flottano accanto
  • L'accept dispatch una transaction al document state
  • Nessuna versione DRAFT — è troppo piccolo per giustificarla

Macro-edit — DRAFT version

Per riscritture strutturali. Es: propose_screenplay_revision({ scope, instruction, label }).

  • Cesare crea una row screenplay_versions con is_draft = true
  • L'editor mostra un banner "DRAFT — v2: tutto in una stanza"
  • Tab "Diff" mostra side-by-side originale vs draft
  • "Promuovi a attiva" sostituisce la version attiva (l'originale resta accessibile da Storico)
  • "Scarta" cancella la row draft

Dalla stringa alle PM positions — la leaf-text walk

File: apps/web/app/features/screenplay-editor/lib/plugins/proposed-edit-decoration.ts · il server propone una stringa find; il client la deve mappare a posizioni ProseMirror per disegnare l'overlay. Il pattern è camminare i nodi text leaf, concatenare il testo, fare indexOf sulla stringa piatta, poi rimappare a coordinate PM. 

interface TextSegment {
  readonly text: string;
  readonly from: number;
}

const collectTextSegments = (doc: PMNode): TextSegment[] => {
  const segments: TextSegment[] = [];
  doc.descendants((node, pos) => {
    if (node.isText && node.text) {
      segments.push({ text: node.text, from: pos });
    }
    return true;
  });
  return segments;
};

// Map a flat-index range over concatenated text back to PM positions.
const mapFlatRangeToPm = (
  segments: TextSegment[],
  flatStart: number,
  flatEnd: number,
): MatchRange | null => {
  let posStart = -1, posEnd = -1, cursor = 0;
  for (const seg of segments) {
    const segEnd = cursor + seg.text.length;
    if (posStart < 0 && cursor <= flatStart && flatStart < segEnd) {
      posStart = seg.from + (flatStart - cursor);
    }
    if (posEnd < 0 && cursor < flatEnd && flatEnd <= segEnd) {
      posEnd = seg.from + (flatEnd - cursor);
    }
    if (posStart >= 0 && posEnd >= 0) break;
    cursor = segEnd;
  }
  // ... (vedi file completo per il null-check finale e il return)
};

Cosa imparare da questo codice

  • Il server non parla mai di PM positions: ragiona su stringhe. Il client porta il peso della mappatura — così se domani cambiamo editor (CodeMirror, plain textarea), il server non cambia di una riga.
  • L'algoritmo è lineare sul numero di leaf, niente regex ricorsive. Su un copione di 100 scene è < 1ms.
  • Se il flat range "straddles" un gap di nodi non-text, ritorna null — fail-safe esplicito invece di decoration sballata.

Perché in-memory store invece di DB

Le proposte vivono in una Map<screenplayId, Bucket> lato server, non in PostgreSQL. Trade-off accettato: se il server riavvia, le proposte pendenti si perdono. Beneficio: zero migrazioni, zero query path, zero garbage collection di proposte abbandonate. Se l'utente perde una proposta, ri-chiede a Cesare — costa $0.015. Una tabella screenplay_proposals con cleanup avrebbe costato giorni di lavoro per un recovery che nessuno usa.

Il pattern in due righe

Mutazione potente = propose_* + UI overlay con ✓/✕. Mutazione triviale (set_budget_cap, add_to_budget) = esecuzione diretta dopo conferma testuale di Cesare. La soglia: "se va male, l'utente se ne accorge subito?" Se sì → diretta. Se no → propose.

7. Errori come valori (neverthrow Result/ResultAsync)

Capitolo corto ma essenziale. Cesare non ha mai un try/catch sui suoi tool. Ogni executor ritorna ResultAsync<ToolResult, CesareError>. Gli errori non sono eccezioni: sono un branch del control flow.

Cosa significa in pratica

// Tool executor
const readSceneByNumber = (
  db: Db, projectId: string, sceneNumber: number,
): ResultAsync<unknown, CesareError> =>
  ResultAsync.fromPromise(
    (async () => {
      const [screenplay] = await db.select()...;
      if (!screenplay) return errPayload(`No screenplay`);
      const [scene] = await db.select()...;
      return scene ?? errPayload(`Scene ${sceneNumber} not found`);
    })(),
    (e) => new CesareError(`Failed: ${e.message}`),
  );

// Loop usage
const result = await args.executor(block, args.db, args.projectId);
if (result.isErr()) {
  toolResults.push({
    type: "tool_result",
    tool_use_id: block.id,
    content: JSON.stringify({ error: result.error.message }),
  });
} else {
  toolResults.push(result.value);
}

Il modello vede l'errore come tool_result strutturato — { "error": "Scene 99 not found" } — e può decidere di ri-provare con un argomento diverso, o di comunicare all'utente. Non c'è "crash silenzioso", non c'è "il loop si interrompe": l'errore è dato, e il modello ragiona su quel dato.

Beneficio dall'UI

Al boundary client (TanStack Query hook), il ResultShape serializzato attraversa il filo. La UI fa ts-pattern.match() esaustivo sui _tag degli errori — CesareError, ForbiddenError, NotFoundError — e TypeScript rifiuta di compilare se ne manca uno. Il toast d'errore è specifico per tag, non generico.

8. Context Engineering — Film Bible (Spec 38)

Questo capitolo racconta come abbiamo risolto quello che internamente chiamiamo il "bug di Roma" — e perché risolverlo ha richiesto di ripensare come il contesto narrativo entra nel prompt di Cesare.

Il bug di Roma

Durante i test di location scouting, Cesare continuava a suggerire location romane per film ambientati altrove — un ristorante di paese nelle Marche, un interno di campagna in Emilia. Il problema non era il modello: era il contesto che gli passavamo.

I documenti narrativi (logline, soggetto, sinossi, scaletta, trattamento) venivano iniettati nel blocco non-cached del prompt — frammentati, senza gerarchia, con frasi tipo "RISTORANTE DA DANTE" che non spiegavano dove fosse il ristorante, in che tipo di comune, con che atmosfera. Il modello non aveva abbastanza segnale geografico e culturale per ancorare i suggerimenti al contesto reale del film.

Root cause

Passi testi grezzi non distillati → il modello estrae il segnale che riesce → il segnale geografico è debole o assente → il modello usa il prior implicito (le grandi città italiane sono la default location mentale per l'italiano medio) → Roma.

La soluzione: tre componenti

Spec 38 introduce tre componenti che lavorano insieme per portare il contesto narrativo nel prompt in forma distillata, stabile e cachabile:

1. Scene Summaries

Ogni scena viene riassunta in un JSON strutturato da Haiku 4.5. Generato lazy on-save con fingerprint anti-stale. Stored in DB. Costo: ~$0.00003/scena.

2. Film Bible

Distillazione a livello progetto che aggrega scene summaries + documenti narrativi in un unico blocco JSON, tramite Sonnet 4.6. Cachato. Costo: ~$0.003/distillazione.

3. Location Prior

formatBibleForLocations(bible) inietta un blocco SETTING PRIOR nel guidance delle locations: dice a Cesare dove è ambientato il film e proibisce esplicitamente suggerimenti fuori contesto.

9. Document Authority — conflitti tra documenti

La bible distilla da più documenti narrativi: logline, soggetto, sinossi, scaletta, trattamento. Su un progetto maturo questi documenti si contraddicono — è normale nel processo di sviluppo di un film.

Esempio concreto: la logline dice "Marco è un uomo di mezza età". Il trattamento, scritto sei mesi dopo, dice "Marco ha 32 anni, ex-militare". La bible deve sapere quale dei due "Marco" usare — e la risposta non è "il più recente nel DB" né "l'ultimo salvato". È il documento con la maggiore autorità.

DOC_AUTHORITY — la gerarchia

File: packages/domain/src/bible/authority.ts 

// Higher index = higher authority.
// A tratment written last month beats a logline written a year ago:
// the project has evolved, the more detailed document wins.
export const DOC_AUTHORITY = [
  "logline",
  "soggetto",
  "synopsis",
  "outline",
  "treatment",
] as const;

export type DocType = (typeof DOC_AUTHORITY)[number];

Il ragionamento è semplice: il trattamento è il documento più elaborato e più tardivo nel processo di sviluppo. Se il trattamento dice che Marco ha 32 anni, il progetto è già andato in quella direzione — la logline è solo il germe originale. Il documento più specifico e più avanzato nel workflow vince.

resolveFact() — risolvere il conflitto

Stesso file. Riceve un array di { value, source } estratti da documenti diversi sulla stessa "fact" (es. l'età di Marco). Ritorna "resolved" con il valore vincente, o "contested" se due documenti alla stessa autorità dicono cose diverse. 

export type FactEntry = {
  readonly value:  string;
  readonly source: DocType;
};

export type ResolvedFact =
  | { status: "resolved";  value: string; winner: DocType }
  | { status: "contested"; values: FactEntry[] };

export const resolveFact = (facts: FactEntry[]): ResolvedFact => {
  if (facts.length === 0)
    return { status: "contested", values: [] };

  // Sort descending by authority index — highest authority first.
  const sorted = [...facts].sort(
    (a, b) => DOC_AUTHORITY.indexOf(b.source) - DOC_AUTHORITY.indexOf(a.source),
  );

  const topAuthority = DOC_AUTHORITY.indexOf(sorted[0].source);
  const topFacts     = sorted.filter(
    (f) => DOC_AUTHORITY.indexOf(f.source) === topAuthority,
  );

  // All top-authority documents agree → resolved.
  const uniqueValues = [...new Set(topFacts.map((f) => f.value))];
  if (uniqueValues.length === 1)
    return { status: "resolved", value: uniqueValues[0], winner: sorted[0].source };

  // Same authority, different values → contested (needs human review).
  return { status: "contested", values: topFacts };
};

I due stati: resolved vs contested

resolved

Il documento con l'autorità più alta è univoco sul valore. La bible usa quel valore e annota da quale documento viene. 

// treatment: "Marco, 32 anni, ex-militare"
// logline:   "Marco, uomo di mezza età"
{ status: "resolved",
  value:  "32 anni, ex-militare",
  winner: "treatment" }

contested

Due documenti alla stessa autorità danno valori diversi. La bible segnala il conflitto. Cesare può indicarlo all'utente invece di scegliere arbitrariamente. 

// outline v1:  "Marco, carabiniere"
// outline v2:  "Marco, ingegnere"
{ status:  "contested",
  values: [
    { value: "carabiniere", source: "outline" },
    { value: "ingegnere",   source: "outline" },
  ] }

Perché treatment batte logline

Il filmmaking è un processo iterativo. Una logline viene scritta nelle prime ore di sviluppo del progetto — è un'idea, non un vincolo. Il trattamento viene scritto dopo settimane o mesi di revisioni, con i personaggi già sviluppati, i luoghi già scelti, la struttura narrativa già definita.

Usare la logline per risolvere un conflitto significherebbe che la prima bozza ha sempre ragione sulla versione finale. È il contrario di come funziona lo sviluppo di un film. DOC_AUTHORITY rispecchia la gerarchia reale del processo creativo: i documenti più elaborati e più tardivi hanno più autorità.

Cosa si guadagna con l'authority order

Senza resolveFact(), Sonnet riceverebbe testi contraddittori nel prompt della distillazione e produrrebbe una bible incoerente — o peggio, ne mixerebbe i valori in modo imprevedibile. Con l'authority order, la distillazione è deterministica: stesso input → stessa bible. Questo è fondamentale per il fingerprint e per la cache.

10. Cosa abbiamo deciso di NON fare

Una buona architettura è anche un elenco di no. Questi sono i principali per Cesare:

Cosa Perché no Quando potrebbe diventare sì
Effect-TS neverthrow copre il 90% dei bisogni in 30 righe di API. Effect-TS porta uno stack di concetti (Layer, Context, Schedule, STM) che non ci serve. Costo cognitivo > beneficio. Mai, salvo che il team cresca a 10+ engineer ML
Agente autonomo (no human approval) Vedi capitolo 6. Un agente che modifica senza conferma perde la fiducia dell'utente. Filmmaker = scrittore = proprietà del testo non negoziabile. Mai sul testo. Forse su task amministrativi (es. "ordina i pin sulla mappa").
Vector store (Pinecone, pgvector) Vedi capitolo 3. Dati strutturati, non c'è similarity search da fare. Se aggiungiamo una knowledge base di template / esempi industriali (script ottimi da imitare).
Fine-tuning custom Sonnet 4 e Haiku 4.5 sono già ottimi sull'italiano e su comprensione narrativa. Il fine-tune costa $$, vincola a un provider, e i guadagni marginali non giustificano la riduzione di portabilità. Se trovassimo un task ricorrente con > 100k esempi etichettati e Sonnet sotto al 70% di accuracy
Streaming come default Cesare è turn-based: l'utente vede una bolla che appare per intera dopo < 3s. Lo streaming complicherebbe il parsing dei marker side-channel e l'esecuzione dei tool. Beneficio percepito = quasi nullo. Se le risposte testuali iniziano a passare i 10 secondi (oggi 1.5-3s)
LLM secondario per routing Il routeModel è un regex. Far decidere a Haiku quale modello usare aggiunge un round-trip $$ e latenza per un problema risolvibile con str.endsWith("?"). Se la heuristic regex fallisce su > 15% dei messaggi misurati

11. Letture consigliate

Tutti questi sono nomi di concetti / pattern, non URL. Cerca i titoli e il provider giusto compare in cima ai risultati.

Anthropic — first-party

  • "Building effective agents" (blog Anthropic, dicembre 2024) — il manifesto su cui si basa l'approccio "augmented LLM + tools + loops" che usiamo. Distingue tra workflows (codice che usa LLM come step) e agents (LLM che pilota l'execution flow). Cesare è ibrido: lo loop è codice rigido, ma le decisioni dentro al loop sono dell'LLM.
  • Anthropic Tool Use docs — la spec ufficiale del tool_use / tool_result block model. Da leggere prima di scrivere uno schema di tool. Include la guida su come formattare input_schema (JSON Schema subset), come gestire tool_result con errori, e il flow stop_reason: "tool_use".
  • Prompt caching guide (Anthropic) — la documentazione del cache_control: ephemeral. Spiega il TTL (~5 minuti), le condizioni di cache hit (prefisso esatto dell'array di blocchi), come misurare gli hit via usage.cache_read_input_tokens, e i vincoli: il blocco cachato deve essere di almeno 1024 token per essere eligibile. Fondamentale per capire perché l'ordine dei blocchi nel system prompt è immutabile — spostare un blocco invalida tutto il prefisso.

Pattern agentici

  • Orchestrator-Workers pattern — Cesare è ispirato a questo: un orchestrator (il loop) sceglie un worker (un tool) in base al contesto, ne consuma il risultato, decide la mossa successiva. È il pattern più portabile e debuggable, e anche il più documentato.
  • Routing pattern — il routeModel implementa una versione semplice (regex-based) del routing, dove un classificatore upstream decide quale executor downstream usare. La variante "LLM classifier" costa di più ma scala meglio su intent space larghi.
  • Reflection / self-critique loops — non li usiamo (vorrebbe dire più iterazioni e quindi più costo) ma sono il prossimo step se mai vorremo "Cesare rilegge la propria proposta prima di mostrarla".

Context Engineering

  • "Prompt caching" (Anthropic docs) — sezione specifica su come strutturare il system prompt per massimizzare i cache hit. Include i casi edge: messaggi multiturno, tool definitions in cache, come il position dei blocchi cache_control determina il prefisso. Spec 38 implementa esattamente la strategia consigliata: blocchi stabili davanti, dinamici in coda.
  • Lazy distillation pattern — il pattern che Spec 38 chiama "bible distillation" è una variante del "lazy RAG": invece di caricare tutti i documenti nel prompt e lasciare che il modello li interpreti on-the-fly, li pre-digerisci in una struttura stabile e usi quella struttura nel prompt. La differenza rispetto al RAG classico: non stai cercando chunks rilevanti per similarità — stai producendo una distillazione completa del progetto che viene aggiornata solo quando cambia il fingerprint. Cerca "pre-computed context" o "offline distillation" per pattern simili in letteratura. Oh Writers lo implementa con: (a) fingerprint composito multi-source, (b) lazy update (background re-distill invece di bloccare l'utente), (c) stale-while-revalidate semantics.

RAG e dintorni

  • "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks" (Lewis et al., 2020) — il paper originale di Facebook AI che ha coniato il termine. Utile per capire cosa stiamo NON facendo e perché.
  • "Lost in the middle" (Liu et al., 2023) — paper Stanford che mostra come gli LLM ignorino informazioni nel mezzo di context window lunghi. È un'altra ragione per cui il lazy-RAG batte il full-payload: meno tokens = più attenzione effettiva sui rilevanti. La bible distillata è densa e strutturata — il modello "spende" la finestra di attenzione su dati già interpretati.

Engineering generale

  • Anthropic — Model Context Protocol (MCP) — è lo standard aperto per esporre tool a un LLM. Cesare non lo usa direttamente (i tool sono interni al monorepo), ma se mai apriamo Cesare a integrazioni terze (Final Draft, Google Drive, Movie Magic) MCP è il punto di partenza.
  • "How to build a million dollar agent" — articoli pratici su costi reali e scaling di sistemi agentic in produzione. Da cercare nel blog Anthropic e nel blog di LangChain.

12. Come tenere viva questa pagina

Questa è una zona di learning persistente, non un report una-tantum. Cambia ogni volta che cambia l'architettura agentic — esempi tipici:

  • Aggiungiamo un nuovo tool a Cesare → aggiorna §2 (lista tool nel loop) e §3 (se è un read_* tool, va nella tabella RAG).
  • Cambia il model router (es. arriva Haiku 5 o Opus 5) → aggiorna §5 con il nuovo bivio di costo e le nuove heuristics. Il regex italiano vive solo lì.
  • Spuntiamo prompt caching su nuovi blocchi → aggiorna §4 con la nuova lista cached vs non-cached e ri-misura il risparmio reale (è nei vernissage/cost-foundation.md).
  • Nuovo pattern propose/accept (oggi: micro PM decoration + macro DRAFT) → aggiungi la terza variante in §6 spiegando trade-off rispetto alle altre due.
  • Cambia il Film Bible (nuovi campi in FilmBibleSchema, nuova logica di distillazione) → aggiorna §8 con lo schema aggiornato e il nuovo flusso. Se cambia la strategia di caching (es. bible in blocco separato) aggiorna anche §4.
  • Decidiamo di fare qualcosa che era nel "NO" di §10 (es. accendiamo lo streaming, o adottiamo MCP) → sposta la riga dalla §10 alla §11 e spiega il perché del cambio: la decisione di non fare è documentata, la decisione di tornarci sopra anche.

La regola è la stessa di CLAUDE.md: la pagina deve sempre riflettere quello che c'è davvero in codice, non l'idea iniziale. Se trovi una sezione che descrive qualcosa che non corrisponde più al codice, è un bug del documento — non del codice.

Come usarla per imparare

Tre livelli di profondità:

  1. Skim del callout finale (§"Riassunto in una pagina") — 30 secondi, capisci l'architettura per la pitch deck.
  2. Lettura sequenziale §1 → §11 — 40 minuti, esci con un mental model completo dei pattern.
  3. Deep dive con il codice aperto — leggi §3 con aperto cesare-read-tools.ts, §5 con aperto cesare-model-router.ts. Ogni capitolo cita esplicitamente i file sorgente per fare il ponte.

Come usarla per spiegare a qualcuno

Per un investor: parti dal callout finale + numeri WOW di §1. Per un tecnico: §2 (tool loop) + §3 (lazy RAG) bastano. Per un designer / product: §6 (propose/accept) è la sezione UX. Per un CFO: §4 + §5 (caching e router) sono sui costi. Per chi vuole capire il "bug di Roma" e come è stato risolto: §8 (context engineering) + §9 (document authority).

Riassunto in una pagina

Cesare è un tool-use loop con max 5 iterazioni. Il contesto è lazy: il system prompt è un indice, i dettagli arrivano via read_* tools. Il prompt è cachato sui blocchi statici (ruolo, film bible, contesto produzione, tool guidance) e dinamico solo sull'ultimo blocco. La Film Bible distilla scene summaries + documenti narrativi in un blocco strutturato stabile, risolvendo i conflitti tra documenti via DOC_AUTHORITY e iniettando un SETTING PRIOR per le locations (fix del "bug di Roma"). Un router puro sceglie Haiku per le domande brevi e Sonnet per le mutazioni. Le modifiche al testo passano sempre per propose / accept, mai auto-apply. Gli errori sono valori (neverthrow), non eccezioni. Niente vector store, niente Effect-TS, niente fine-tuning, niente streaming default.
